# First pilot on one OVH A10

This is a separate **Q4 pilot** for the available OVH a10-45: one A10 with 24 GB
VRAM, approximately 42 GB system RAM, 30 vcores and 400 GB disk. The existing
[two-V100S Q8 experiment](ovh.md) stays available with its original launchers.
The commands below validate the real machine before using the scored problems.

## What stays the same

Use the same ten statement-only problems and three methods: direct best-of-three,
the sequential harness, and three independent harness proof attempts. Each
method keeps a **60,000 generated-token ceiling per problem**, including thinking
and reviews. Each portfolio branch receives 17,952 tokens and selection receives
6,144. Seeds, solver temperature 0.6, top-p 0.95, zero-temperature reviews and
blinded human grading are unchanged. One replicate still means 30 jobs and at
most 1.8 million generated tokens.

The A10 runs **one branch at a time**. The saved arm name `parallel` still denotes
the three-branch portfolio algorithm; `branch_concurrency: 1` explicitly records
that those branches execute sequentially. This tests the effect of independent
attempts and selection on mathematical quality, not parallel inference speed.
Waiting branches are not started and do not lose their individual time allowance.
The separate `sequential` arm remains one long proof search; it does not become
identical to three separate searches merely because both use one GPU slot.

All arms use the same Q4 weights. Report these results separately from Q8/BF16:
quantization can change outputs and mathematical accuracy. Equal generated-token
ceilings do not imply equal input-token work or equal elapsed time.

## Prepare the existing server

Your host image can differ from the container's Ubuntu 22.04 base. The screenshot
shows Ubuntu 26.04; do not install packages from an older Ubuntu distribution on
that host. A working NVIDIA driver and Docker GPU runtime are required.

1. On the A10 host, run `nvidia-smi`. It must identify one A10 with roughly 24 GB.
   If the driver is missing, follow the [Ubuntu Server driver guide](https://ubuntu.com/server/docs/how-to/graphics/install-nvidia-drivers/)
   for the installed Ubuntu release. Check driver compatibility with CUDA 12.9.
   The compute-driver installation may also need the matching
   `nvidia-utils-<branch>-server` package to provide `nvidia-smi`.
2. Install Docker and the [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html).
   Ensure the current shell can run Docker with GPU access. No host CUDA compiler
   installation is needed: compilation happens inside the pinned container.
3. Obtain this repository on the server. If it is still private, authenticate
   Git access or copy the checkout from your Mac; no credentials belong in the
   benchmark files. From an authenticated shell:

   ```bash
   git clone https://github.com/vincentboulard/Square-Harness.git
   cd Square-Harness
   python3 -m venv .venv
   source .venv/bin/activate
   python -m pip install -e .
   mkdir -p "$HOME/square-runs/a10-server" "$HOME/square-data"
   ```

Keep about 100 GB free for weights, build layers and logs. Use persistent terminal
sessions, for example tmux, so SSH disconnection does not end the experiment.

## Build, download, launch

Run these commands from the checkout. They use the A10 profile; the V100 scripts
and model files are separate:

```bash
bash scripts/build-llama-a10.sh
bash scripts/download-llama-a10.sh
set -o pipefail
bash scripts/serve-llama-a10.sh 2>&1 | tee "$HOME/square-runs/a10-server/startup.log"
```

Keep the server running. The model defaults to
`~/.cache/square-harness/models-a10`; the launch record is
`~/square-runs/a10-server/launch.json`. The model download is hash-checked,
resumable, and approximately 16.8 GB. The served port is bound to host loopback.
Inspect startup logs for all layers on CUDA0 and one 32,768-token slot.
The A10 launcher enables the logging level needed to retain layer-offload and
GPU-buffer diagnostics in the pinned llama.cpp revision.

If startup fails from GPU memory pressure, first try a smaller batch in a new
server session:

```bash
bash scripts/serve-llama-a10.sh --batch-size 128 --ubatch-size 32
```

Keep 32K context, Q4 weights and one slot fixed. Do not reduce to 16K: the existing
direct-answer allocation alone can reach 17,952 tokens. If the 32K configuration
cannot pass acceptance even with smaller batches, retain the failure report and
revise the experimental condition explicitly before proceeding.

## Acceptance and rehearsal

In another terminal, enter the checkout and activate `.venv`:

```bash
source .venv/bin/activate
python scripts/smoke-serving.py \
  --backend llamacpp --host http://127.0.0.1:8000 --model square-qwen-a10 \
  --ctx 32768 --parallel 1 \
  --launch-record "$HOME/square-runs/a10-server/launch.json" \
  --output "$HOME/square-runs/a10-server/acceptance.json"
```

The report must have `accepted_for_benchmark: true`. It checks reasoning, tool
calls, JSON reviews, streamed token usage, output caps, and one-slot decoding at
short and approximately 30,000-token inputs. Its `capacity_mode: sequential`
does not claim parallel decoding. These are software/capacity tests, not proof
verification. If repeating after any launch change, use a new report filename
and pass that new file to subsequent commands.

Rehearse the three methods on two synthetic problems:

```bash
python -m mathagent.benchmark --init-smoke "$HOME/square-data/a10-smoke-statements"
python scripts/run-a10-benchmark.py \
  --manifest "$HOME/square-data/a10-smoke-statements/manifest.json" \
  --output "$HOME/square-runs/a10-rehearsal-001" \
  --acceptance "$HOME/square-runs/a10-server/acceptance.json"
```

The runner permits only one model request at a time. The time guards default to
43,200 seconds per job, 7,200 per request and 3,600 reserved for selection. Three
serialized branches receive equal maximum execution windows of 13,200 seconds,
starting when each is dispatched. These are generous ceilings, not predictions
of runtime or a cloud spending cap. Calibrate on synthetic data before scoring;
freeze any changes consistently across all methods. Inspect and report binding
time guards as well as consumed tokens. Interruptions keep their usage records;
parent runs do not automatically resume.

## Launch the ten-problem pilot

Copy **only** `pilot-10-v1` from your prepared private benchmark directory to
`~/square-data/` on the server. Keep annotated sources, hints and grading
references elsewhere. For example, from your Mac:

```bash
scp -r /Users/vincent/Documents/SquareHarness/benchmarks/pilot-10-v1 \
  ubuntu@YOUR_SERVER:~/square-data/
```

On the server, first validate the frozen plan without inference:

```bash
python scripts/run-a10-benchmark.py \
  --manifest "$HOME/square-data/pilot-10-v1/manifest.json" \
  --output "$HOME/square-runs/pilot-a10-q4-001" \
  --acceptance "$HOME/square-runs/a10-server/acceptance.json" \
  --dry-run
```

Then run the same command without `--dry-run`. It refuses a missing/mismatched
acceptance report or wrong model/profile and rechecks the running server before
scoring. Run directories are one-shot and never overwritten. Every plan retains
the immutable model/image identities, exact dataset hashes and actual scheduling.

Results use the same layout and [blinded grading protocol](benchmark.md). Copy
all results and server logs back to your Mac, verify the backup, and then manage
the instance according to your chosen billing workflow. No GPU benchmark result
or throughput estimate is implied by the local automated test suite.
