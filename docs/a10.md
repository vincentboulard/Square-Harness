# Retained A10 llama.cpp profile

This is the original one-A10 Q4 serving alternative. For the fast W4A16/DFlash2
configuration, use [HyperQwen on A10](hyperqwen-a10.md). Version 0.5 retains the
hardware setup but replaces the old portfolio experiment with `raw-single` and
`proof`.

## Frozen serving settings

| Setting | Value |
| --- | --- |
| Hardware | One NVIDIA A10, 24 GB VRAM; original host approximately 42 GB RAM |
| Text model | Qwen3.8-27B Q4_K_M, approximately 16.8 GB |
| Model SHA-256 | `f5f1dd8920d417aac2718b0bda3403da274301efdd6760b4f0f4b864ff2ad57d` |
| llama.cpp | `2145525a4081d66ff1a87cf43ef809f95a85ac0c` |
| Build | CUDA 12.9.1, SM86 |
| Placement | All model layers on the single GPU |
| Context / slots | 32,768 input-plus-output tokens / one slot |
| KV cache / Flash Attention | F16 / off |
| Endpoint / model alias | `http://127.0.0.1:8000` / `square-qwen-a10` |

The authoritative identities are in
[`deployment/llama-a10.lock.json`](../deployment/llama-a10.lock.json).
Context shifting and automatic fit reduction are disabled. No vision projector
is needed. A pinned configuration is not a guarantee of GPU fit; inspect actual
placement and complete the serving checks.

## Setup and check

Use an existing Linux host with a working NVIDIA driver, Docker and NVIDIA
Container Toolkit. `nvidia-smi` should identify the A10. Keep about 100 GB free
for model weights, images and logs. Install the harness as in the
[README](../README.md), then run from the checkout:

```bash
mkdir -p "$HOME/square-runs/a10-server"
bash scripts/build-llama-a10.sh
bash scripts/download-llama-a10.sh
set -o pipefail
bash scripts/serve-llama-a10.sh 2>&1 | tee "$HOME/square-runs/a10-server/startup.log"
```

The hash-checked download defaults to `~/.cache/square-harness/models-a10`.
The launch record is `~/square-runs/a10-server/launch.json`; keep the server
running in a persistent terminal. In another activated terminal:

```bash
python scripts/smoke-serving.py \
  --backend llamacpp --host http://127.0.0.1:8000 --model square-qwen-a10 \
  --ctx 32768 --parallel 1 \
  --launch-record "$HOME/square-runs/a10-server/launch.json" \
  --output "$HOME/square-runs/a10-server/acceptance.json"
```

Inspect GPU placement, context and acceptance results. A changed launch needs a
new acceptance record. These checks concern serving, not mathematical correctness.

## v0.5 benchmark

This 32k-context profile uses **16,384 tokens for both initial solves**, 8,192
for verification and a 90,000-token proof-job ceiling over at most three attempts.
It is a different resource condition from the 40k-context HyperQwen profile.
Do not request a 32,768-token completion inside a 32,768-token context: the prompt
also needs space.

After a small [software smoke test](benchmark.md#software-smoke-test), use:

```bash
python scripts/run-a10-benchmark.py \
  --manifest "$HOME/square-data/pilot-10-v1/manifest.json" \
  --output "$HOME/square-runs/a10-v05-001" \
  --launch-record "$HOME/square-runs/a10-server/launch.json" \
  --acceptance "$HOME/square-runs/a10-server/acceptance.json" \
  --dry-run
```

Inspect the plan before removing `--dry-run`. One problem/arm runs at a time.
Keep statements private and copy only the statement-only dataset to the server.
Preserve results and logs before retiring the instance. Earlier Q4 results belong
to the old source snapshot and are not measurements of v0.5.
